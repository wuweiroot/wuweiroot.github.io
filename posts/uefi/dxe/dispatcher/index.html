    Dispatcher 与 Depex：驱动为什么会被调度（或不被调度）

    September 17, 2026

    DXE 阶段的驱动由 Dispatcher 统一发现与启动，启动顺序由 Depex（依赖表达式）决定。本文整理这套机制与排查方法（以 EDK II 的 Dxe 内核为例，行号随版本略有差异）。

    Dispatcher 的职责#

    1. 从 FV 中发现驱动文件（FFS 中的 DXE driver）；
    2. 读取该驱动的 Depex，判断当前是否可调度；
    3. 可调度则 LoadImage + StartImage，并处理 BEFORE / AFTER 的顺序要求。

    三个核心链表#

    变量 位置 作用
    mDiscoveredList Dispatcher.c:40 已发现但尚未调度的驱动条目（不释放）
    mScheduledQueue Dispatcher.c:46 依赖已满足、待启动的驱动队列
    mFvHandleList Dispatcher.c:51 已处理过的 FV，避免重复发现

    三阶段模型#

    Dispatcher.c 顶部的模块注释（:1-26）把调度分成三步：

    阶段 关键函数 行为
    发现 CoreFwVolEventProtocolNotify（:1246）→ CoreAddToDriverList（:903） FV 协议安装事件触发；遍历 FFS，把驱动加入 mDiscoveredList；A PRIORI 文件中的驱动直接入队
    调度 CoreDispatcher（:405） 主循环：从 mScheduledQueue 取一条 → LoadImage + StartImage；队列空后重扫 mDiscoveredList，把 Depex 已满足的加入队列
    排序 CoreInsertOnScheduledQueueWhileProcessingBeforeAndAfter（:624） 入队时处理 BEFORE / AFTER 的相对顺序

    Depex 段的读取与预处理：CoreGetDepexSectionAndPreProccess（:240），读取 EFI_SECTION_DXE_DEPEX（:254）。

    Depex：依赖表达式#

    操作码定义在 MdePkg/Include/Pi/PiDependency.h：

    值 操作码 含义
    0x00 EFI_DEP_BEFORE 必须排在某驱动之前（只能单独出现）
    0x01 EFI_DEP_AFTER 必须排在某驱动之后（只能单独出现）
    0x02 EFI_DEP_PUSH 检查指定协议（可带 handle）是否存在，向栈压入 TRUE / FALSE
    0x03 / 0x04 / 0x05 EFI_DEP_AND / OR / NOT 布尔运算（栈式求值）
    0x06 / 0x07 EFI_DEP_TRUE / FALSE 常量
    0x08 EFI_DEP_END 表达式结束
    0x09 EFI_DEP_SOR Schedule On Request：需外部显式请求才调度（仅 DXE 驱动）

    求值实现（Dependency.c）：

    • 预处理 CorePreProcessDepex（:161）：识别 SOR（:168）、BEFORE（:174）、AFTER（:176）；
    • 主求值 CoreIsSchedulable（:251）：使用布尔求值栈 PushBool（:91）/ PopBool（:129），逐操作码处理 —— PUSH（:347）、AND（:381）、OR（:403）、NOT（:425）、TRUE（:441）、FALSE（:451）、END（:461）。

    PUSH 的语义是"该协议（在指定 handle 上）是否已经安装"：已安装压 TRUE，否则压 FALSE。因此 Depex 等价于"依赖的协议是否已就位"。

    A PRIORI 文件#

    FV 中的 A PRIORI 文件列出的驱动不参与 Depex 判断，直接进入 mScheduledQueue，用于强制某些驱动先跑（例如提供架构协议的驱动）。

    驱动没有被调度：排查清单#

    1. 没被打进 FV：FDF 是否包含该模块、FV 布局是否正确；
    2. Depex 不满足：依赖的协议没有提供者、AFTER 的目标驱动没跑、SOR 没有被显式调度；
    3. 架构协议缺失：BS/RT 服务表不完整会影响后续驱动；
    4. 顺序被挡：A PRIORI、BEFORE / AFTER 的组合把它排到了后面；
    5. 确认手段：DEBUG 构建下 CoreDisplayDiscoveredNotDispatched()（DxeMain.c:577）会打印"已发现但未调度"的驱动列表，这是最直接的线索。

    与 UEFI Driver Model 的区别#

    类型 行为
    DXE driver 入口点被 StartImage 调用后即开始工作
    UEFI driver（实现 EFI_DRIVER_BINDING_PROTOCOL） 入口点通常只安装 Binding 协议，设备初始化要等 ConnectController 调用其 Supported() / Start()

    后者的连接时机见 StartImage 与 ConnectController。
