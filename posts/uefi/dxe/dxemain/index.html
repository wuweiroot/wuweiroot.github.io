    DXE Core 启动流程：DxeMain 做了什么

    September 17, 2026

    DxeMain 是 DXE 阶段的入口函数，负责把"能运行驱动"的环境准备好，随后把控制权交给 Dispatcher 和 BDS。本文按执行顺序整理它的流程与关键位置（以 EDK II 的 Dxe 内核为例，行号随版本略有差异）。

    输入与产物#

    内容
    输入 HobStart：PEI 阶段通过 HOB 链表传下来的资源描述（可用内存、FV、架构相关数据）
    产物 Boot Services / Runtime Services / DXE Services 三张表、已从 FV 发现并调度的驱动、交给 BDS 的控制权

    函数原型：VOID EFIAPI DxeMain (IN VOID *HobStart)（MdeModulePkg/Core/Dxe/DxeMain/DxeMain.c:257）。

    启动流程（按执行顺序）#

    阶段 位置 做什么
    CPU 环境 :276-288 从 HOB 取向量移交信息，安装异常处理；初始化调试代理
    内存服务 :293 CoreInitializeMemoryServices()：用 HOB 建立可用内存与分配池
    System/Runtime 表 :301-307 从模板分配 EFI_SYSTEM_TABLE 与 EFI_RUNTIME_SERVICES（分配在 RuntimeServicesData 类型）
    Image 服务 :317 CoreInitializeImageServices()：LoadedImage、DevicePath 等基础
    GCD 服务 :323 CoreInitializeGcdServices()：内存空间与 IO 空间的 GCD 描述符
    库构造函数 :329 ProcessLibraryConstructorList()
    配置表 :368-391 InstallConfigurationTable()：DXE Services 表、HOB 链表、MemoryTypeInformation、（可选）固定地址加载表
    状态码与调试信息 :396-411 上报 DXE_CORE_PC_ENTRY_POINT；建立调试镜像信息表
    事件服务 :476 CoreInitializeEventServices()
    内存属性与保护 :481-482 Memory Attributes Table、Memory Protection（只读/Guard 等）
    解压协议 :519-525 安装 Decompress Protocol
    架构协议通知 :532 CoreNotifyOnProtocolInstallation()：注册对架构协议安装的通知
    FV 协议 :537-547 FwVolBlockDriverInit()、FwVolDriverInit()、InitializeSectionExtraction()：为 HOB 中每个 FV 产出读写与解包能力
    调度器初始化与运行 :552-563 CoreInitializeDispatcher() → CoreDispatcher()（详见 Dispatcher 与 Depex）
    收尾校验 :569-594 DEBUG 下打印缺失的架构协议与未调度驱动；CoreAllEfiServicesAvailable() 校验协议齐备，缺失则上报 major error
    交接 BDS :599-613 上报 PC_HANDOFF_TO_NEXT；调用 gBds->Entry(gBds)；BDS 不应返回，返回则 CpuDeadLoop()

    三张服务表#

    DXE Core 自身实现三张表（在 DxeMain.c 前部以静态表定义）：

    表 内容 说明
    Boot Services Dispatch、InstallConfigurationTable、SetTimer、内存/事件/协议相关服务 部分表项直接指向 Core 内部实现（如 Dispatch → CoreDispatcher）
    Runtime Services 变量、时间、复位等 需要在退出启动服务后仍可用，相关数据放在 RuntimeServicesData
    DXE Services GCD、调度、驱动管理相关服务 通过配置表 gEfiDxeServicesTableGuid 暴露

    这些表不是一次性填满的：部分表项要等对应的架构协议（如定时器、看门狗、运行时、CPU）被提供者安装后才可用。

    架构协议的"填空"机制#

    • CoreNotifyOnProtocolInstallation()（:532）为各架构协议 GUID 注册通知；
    • 提供者安装协议 → 通知被触发 → 相应服务项被填入 BS/RT 表；
    • CoreAllEfiServicesAvailable()（:583）做最终校验：若架构协议不齐，说明服务表不完整，上报 EFI_ERROR_CODE | EFI_ERROR_MAJOR 并触发断言。

    与调度器的交接点#

    DxeMain()
  ├─ 准备：内存 / GCD / 事件 / FV 协议 / 服务表 / 内存保护
  ├─ CoreInitializeDispatcher()            DxeMain.c:552
  ├─ CoreDispatcher()                      DxeMain.c:563   ← 从这里开始跑驱动
  ├─ CoreAllEfiServicesAvailable()         DxeMain.c:583
  └─ gBds->Entry(gBds)                     DxeMain.c:607   ← 交给 BDS

    要点：

    1. DxeMain 不做具体硬件初始化（PCI 枚举、控制台、启动项都不在这里），它只负责把运行驱动所需的环境准备好；
    2. 驱动全部由 Dispatcher 依据 Depex 决定顺序并启动；
    3. 控制台、启动项与设置界面属于 BDS 阶段。

    排查提示#

    • 卡在某个阶段：可用 DXE_CORE_PC_ENTRY_POINT（:396）与 PC_HANDOFF_TO_NEXT（:599）两个进度码判断是"还没进 DXE 主体"还是"已进入调度/交接"；
    • 服务缺失：若出现架构协议缺失的断言，先看对应协议的提供者是否被包含进 FV、Depex 是否满足；
    • 驱动没跑：先看 CoreDisplayDiscoveredNotDispatched()（:577，DEBUG 构建）是否把它列出来，再按 Dispatcher 与 Depex 的清单排查。
