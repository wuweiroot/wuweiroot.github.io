    RAS 模块总结：错误源、APEI 表与通知路径

    September 16, 2026

    本文整理 BIOS 侧 RAS 模块的结构：错误来源分类、APEI 四张表的作用与数据方向、CPER 记录格式、SMI/SCI/NMI 通知路径、表的安装与存储服务实现，以及问题定位顺序。

    RAS 的职责边界#

    维度 含义 典型手段
    Reliability 不出错 / 少出错 ECC、CRC、链路重传
    Availability 出错后仍可用 内存页离线、备用 rank、降级重训
    Serviceability 出错后可定位 错误记录、BMC SEL、OS 日志

    固件在 RAS 链路中的动作：

    接管   硬件报错时取得控制权
记录   生成规范格式的错误记录
上报   通知 OS（APEI/WHEA）与 BMC（SEL）
持久化 必要时写入非易失存储，重启后可读

    错误修复动作主要在 OS 或硬件侧完成（页离线、DRAM 行修复），固件不承担修复职责。

    处理器侧错误报告#

    • Machine Check 机制按 bank 组织。每个 bank 包含：状态寄存器（错误码、严重级别、溢出标志、地址有效位）、地址寄存器、Misc 寄存器（通道、位号、syndrome 等，厂商相关）、bank 归属标识。
    • CE（可纠正）：硬件已纠正，处理方式为计数、阈值、预警。
    • UE（不可纠正）：数据不可信，需隔离并上报 OS。
    • CE 上报路径可选：
      • 处理器中断直接上报 OS；
      • 固件屏蔽后转为 SMI 统一处理，可先做阈值统计、隔离、写 SEL，代价是 SMI 开销，必须限流。

    APEI：四张表#

    表 作用 数据方向 注意点
    HEST 描述错误源与通知方式（含中断向量） 固件写、OS 读 向量为 0 时，表存在但错误不会送达 OS
    BERT 记录固件阶段发生、OS 启动前无法上报的错误 固件写、OS 读 仅覆盖启动阶段，不是运行期错误表
    ERST 提供错误记录的持久化读写接口（串行化指令） 固件提供服务、OS 调用 本质是服务而非静态表，需要维护状态机
    EINJ 错误注入接口 固件提供、工具调用 注入能否成功取决于底层支持

    CPER 记录格式#

    Record Header
  + Section Descriptor[]   类型、偏移、长度
  + Section[]              Processor / Memory / PCIe / Generic

    Memory Section 只保证提供错误类型与物理地址；“物理地址 → 器件 → 通道 → DIMM → 机箱丝印"由平台补充，通常写入 Generic Section 或 BMC SEL。

    OS 与 BMC 是两条独立的消费路径，需要分别确认。

    通知路径#

    手段 处理者 OS 可见性 适用场景
    SMI 固件（SMM） 不可见，由固件决定是否转告 需要固件先统计、隔离、记录
    SCI OS（ACPI 中断 → GHES） 可见 常规通知，交由 OS 处理
    NMI OS 可见，优先级高 UE / 致命错误
    CMCI OS（处理器中断） 可见 CE 直接上报，不经固件

    常见组合：SMI 接管 → 生成记录 → 通过 SCI 或 NMI 通知 OS。HEST 中描述的通知方式必须与实际实现一致。

    处理流程#

    sequenceDiagram
    participant HW as 硬件错误源
    participant SMM as 固件（SMM）
    participant MEM as 错误状态块 / CPER
    participant OS as OS（APEI/WHEA）
    participant BMC as BMC（SEL）

    HW->>SMM: 置错误寄存器、触发 SMI
    SMM->>SMM: 严重级别判定、地址翻译、阈值与限流
    SMM->>MEM: 追加 CPER 条目并更新长度与状态位
    SMM-->>OS: NMI / SCI（与 HEST 描述一致）
    OS->>MEM: 读取错误状态块
    OS->>OS: 页隔离 / 进程处理 / 记录日志
    SMM-->>BMC: 写入 IPMI SEL（含定位字段）
    Note over SMM,MEM: 需要持久化时通过 ERST 写入非易失存储

    其中第 3 步决定"报了是否有用”（能否定位），第 6 步决定"重启后是否还能查"。

    表的安装#

    APEI 表通过 ACPI 表协议安装：

    • 协议定义：MdePkg/Include/Protocol/AcpiTable.h（EFI_ACPI_TABLE_PROTOCOL）
    • 参考实现：MdeModulePkg/Universal/Acpi/AcpiTableDxe/
    • 结构定义：MdePkg/Include/IndustryStandard/Acpi6x.h
    • OS 侧位置：Linux /sys/firmware/acpi/tables/；Windows 由 WHEA 消费

    ERST 串行化指令的链路：

    OS 驱动 → ACPI 方法 / 寄存器接口 → 固件侧服务（通常在 SMM） → 非易失存储（SPI Flash 等）

    该链路跨 OS / 固件 / 存储三层，属于状态机实现。

    实现注意事项#

    1. 失败路径必须复位状态位（Busy / Operation），否则 OS 侧轮询不会结束。
    2. SMM 只能访问 SMRAM；来自外部的 buffer 先校验，可使用 SmmIsBufferOutsideSmmValid()（MdePkg/Include/Library/SmmMemLib.h）。
    3. SMM 内不调用 Boot / Runtime Services（gBS、gRT）。
    4. 高频 CE 需要限流（时间窗或计数）。
    5. 上报通道失败需要降级记录，不应静默丢弃。
    6. 已被 OS 消费的结构只能追加字段，不能改序、改义。

    问题定位顺序#

    1  表是否安装        HEST / BERT / ERST
2  描述是否正确      HEST 的错误源与通知方式（向量非 0）
3  固件是否收到     串口日志 / 状态码
4  记录是否生成     CPER 是否组装完成
5  上报是否成功     SEL 写入、NMI / SCI 是否发出
6  OS 是否消费      dmesg / WHEA 日志
    # Linux：表是否安装
ls -l /sys/firmware/acpi/tables/ | grep -Ei 'bert|hest|erst|einj'

# Linux：内核是否报告错误
dmesg -T | grep -iE 'apei|whea|mce|edac|hardware error'

# Linux：RAS 守护进程与 ECC 统计
rasdaemon --foreground
edac-util -v
    # Windows：WHEA 事件
wevtutil qe Microsoft-Windows-WHEA-Logger /c:20 /rd:true /f:text
    # BMC 侧
ipmitool sel list

    验收标准#

    1. 不丢：该上报的错误必须送出，通道失败需留痕。
    2. 不乱：格式符合规范，OS 可解析，状态机不会卡死。
    3. 能定位：物理地址可翻译为具体机器位置（CPU / 通道 / DIMM）。
