    错误记录到 BMC：CPER 与 IPMI SEL 的映射

    September 16, 2026

    同一份错误，OS 侧看到的是 CPER（APEI/WHEA），运维侧看到的是 BMC 的 SEL（System Event Log）。两者字段体系不同，固件需要做一次转换。本文整理这次转换的字段映射与工程注意点。

    两条消费路径#

    路径 载体 消费者 特点
    OS CPER（由 APEI 表描述） WHEA / APEI 驱动、RAS 守护进程 结构化、字段多、可承载原始数据
    运维 IPMI SEL BMC、带外管理系统 字段少、语义固定、需与 BMC 对齐

    固件在处理完错误后通常两条都发：CPER 用于 OS 精确处理，SEL 用于带外可见与事后追溯。只做一条，必然有一侧"什么都看不到"。

    SEL 记录的基本构成#

    一条系统事件记录（System Event，Record Type 0x02）主要包含：

    字段 说明
    Record ID / Timestamp 记录编号与时间（由 BMC 侧管理）
    Generator ID 事件产生者
    Sensor Type / Sensor Number 传感器类别与编号（定位的基本维度）
    Event Dir / Event Type 事件方向与类型（如断言/解除、可纠正/不可纠正/致命）
    Event Data 1 / 2 / 3 三个字节的事件数据，OEM 可用

    写入方式是通过 IPMI 命令追加记录（Storage 网系的添加 SEL 条目命令），存储与容量管理由 BMC 负责。

    错误类别到 SEL 的映射#

    错误类别 事件类型建议 Event Data 建议内容
    内存 CE 可纠正 器件编号、通道、错误计数
    内存 UE 不可纠正 / 致命 器件编号、通道、地址高位或页号
    PCIe CE 可纠正 端口/设备标识、错误类型
    PCIe UE 不可纠正 / 致命 端口/设备标识、AER 状态摘要
    处理器错误 可纠正 / 不可纠正 处理器编号、bank、错误类型

    Sensor Type / Sensor Number 的具体取值需要与 BMC 侧约定（多数平台走 OEM 定义）。约定一旦确定就是接口，改动需要两侧同步。

    定位信息放在哪#

    SEL 字段有限，定位信息应优先放"能让运维直接行动"的内容：

    1. Event Data 1：器件类别与编号（哪颗 CPU / 哪个器件）
    2. Event Data 2：通道或槽位
    3. Event Data 3：错误类型、严重级别、计数

    若 BMC 与带外界面支持可读文本，则把"人能看懂的位置描述"放在文本字段里——这与 CPER 中 FruText 的作用一致：编码适合机器，文本适合人。

    上报策略#

    • 一条错误一条 SEL 会刷屏：CE 在故障时可能瞬间产生大量记录，应先在固件侧聚合或限流，再决定上报（限流做法见 可纠正错误的阈值与限流）。
    • UE 与致命错误不参与限流：必须实时上报。
    • 写失败要留痕：SEL 满、BMC 未就绪、命令超时都属于常见情况，至少要降级记一条本地日志，不能静默丢弃。

    实现注意#

    1. SMM 内发起 IPMI 命令不要无限等待，要有超时上限，否则会阻塞 SMI 处理。
    2. 写失败需记录返回码，便于区分"没报"与"报了但 BMC 没收"。
    3. 时间戳来源要明确：RTC 不可用时，BMC 通常会自行补时间，固件侧不应依赖本地时间。
    4. OEM 字段的解释权在 BMC 与运维工具侧，固件与 BMC 必须就字段含义达成一致并落到文档。
    5. SEL 容量有限，BMC 一般按覆盖最旧记录处理——固件侧不能假设"SEL 一定写得进去"。

    排查顺序#

    1  固件是否发出 IPMI 命令     串口日志 / 命令返回值
2  命令是否成功              完成码
3  BMC 侧是否可见            ipmitool sel list / BMC 界面
4  字段解读是否一致          记录中的器件/通道与实际位置对照
    # BMC 侧查看
ipmitool sel list
ipmitool sel elist        # 带更详细的字段解析
