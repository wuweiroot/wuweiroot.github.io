    可纠正错误的阈值与限流：工程做法

    September 16, 2026

    可纠正错误（CE）在故障时可能高频产生。既不能每条都上报，也不能完全不报，因此需要阈值与限流两套机制配合。本文整理这两者的语义、复位规则与常见缺陷。

    为什么需要阈值#

    • CE 由硬件纠正，系统仍在运行；但高频 CE 往往预示着器件劣化，需要在演化为 UE 之前暴露出来。
    • 每条 CE 都进 SMM、都写 SEL、都通知 OS，会带来明显开销（SMI 进入退出、Flash 写入、日志刷屏）。

    因此策略是：累计到一定程度再上报，并保证上报内容能定位到具体器件。

    阈值的三层语义#

    层次 定义 典型用途
    累计计数阈值 同一错误源累计 N 条后上报 缓慢劣化的器件
    时间窗阈值 窗口 T 内达到 N 条后上报 突发错误
    模式选择 累积模式 / 突发（风暴）模式二选一或并存 不同故障形态

    需要明确的关键点：两种模式的关系。若实现成互斥，打开其中一种会让另一种失效；这在现场表现为"阈值设了但不生效"。设计时应明确：

    • 两者是"或"关系（任一满足即上报）；
    • 还是"分级"关系（先累计，达到窗口条件再升级上报）。

    计数与复位规则#

    • 清零时机必须明确：上报后清零 / 时间窗滑出清零 / 系统复位清零。
    • 若上报后忘记清零，现象是"只报一次，之后再多的错误都看不到"。
    • 若窗口滑出机制实现成固定刻度，会出现"刚好跨刻度"的抖动，建议用滑动窗口或时间戳差值。
    • 计数要有饱和处理（达到上限后不再增加），避免回绕。
    • 计数粒度：按错误源独立计数（内存按通道/DIMM、PCIe 按端口），不要用一个全局计数覆盖所有来源，否则会丢掉定位信息。

    限流的实现方式#

    常用两种：

    方式 行为 适用
    漏桶 / 令牌桶 单位时间放行固定条数，超出部分丢弃或合并 抑制刷屏
    抑制窗口 触发一次上报后进入静默期，期内只累计不报 避免重复上报同一器件

    规则建议：

    1. UE 与致命错误不参与限流，必须实时上报。
    2. 限流丢弃的记录要有计数，并在解除抑制后汇总上报（例如"静默期内另有 N 条 CE"）。
    3. 限流参数与阈值参数分开配置，避免互相干扰。

    与 OS 侧策略的关系#

    OS 侧（WHEA / EDAC / RAS 守护进程）通常也有自己的阈值与策略。固件上报过密会导致 OS 日志刷屏，甚至触发 OS 侧的错误处理动作。

    合理分工：

    • 固件：早期预警 + 精确定位（哪个器件、哪个位置）+ 带外可见（SEL）
    • OS：页隔离、进程处理、长期统计

    配置项设计建议#

    1. 每项都有明确默认值、取值范围、单位（条 / 秒 / 条每秒）与生效时机（立即或下次启动）。
    2. “关闭阈值"的语义要写清楚：是关闭自动上报，还是连记录也关。建议只关闭上报，记录仍然保留。
    3. 运行期把当前生效值打到日志里，便于"自证配置”——否则现场只能靠猜。
    4. 配置改动要有清单，多平台共用基线时尤其如此。

    常见缺陷#

    1. 两种阈值模式互斥，导致其中一个永远不生效。
    2. 上报后未清零计数，只上报一次。
    3. 时间窗用固定刻度，产生周期性漏报或重复上报。
    4. 计数溢出回绕，永远达不到阈值。
    5. 阈值改动只更新了其中一个平台副本，多机型行为不一致。
    6. 关闭阈值时把 UE 上报一并关闭。
    7. 限流把 UE 也一起抑制，导致致命错误延迟上报。

    验证方法#

    • 注入或压测 CE，观察：上报条数、SEL 条数、OS 侧日志密度是否符合预期。
    • 打开/关闭阈值各跑一遍，确认行为与配置文档一致。
    • 检查"上报后复位"：连续触发两轮错误，确认第二轮仍会上报。
    • 检查限流例外：限流生效期间制造一条 UE，确认仍然实时上报。
